# ADR-0003：固定请求 320k 档，零转码，不依赖 ffmpeg

- 状态：**已接受 · 已实测验证**（2026-07-26 spike）
- 日期：2026-07-26

## 背景

需求为「下载之后直接转化成 MP3」。字面理解会导向一条重链路：下载 → 解码 → 重编码为 MP3，需要 ffmpeg。

而跨平台分发（ADR-0002）意味着内置 ffmpeg 要为 macOS arm64、macOS x64、Windows x64 各备一份二进制，安装包增加约 150MB，并需论证 ffmpeg 许可与本项目 MIT 许可的兼容性。

关键观察：`song/url` 接口**带音质档位参数**。据社区记录，`standard` / `higher` / `exhigh` 各档服务端直接返回 **mp3**（exhigh 为 320k），仅 `lossless` / `hires` 返回 flac。

## 决策

**固定请求 320k 档，下载到的 mp3 直接落盘，全程不做任何音频编解码。**

具体走 weapi 的 `song/enhance/player/url`，以 `br=320000` 表达音质，而非 eapi 的
`song/url/v1` + `level=exhigh`（原因见 ADR-0006 的实测记录）。

「转化成 MP3」在本项目中的准确含义是「**输出文件一律是 .mp3**」，而非「一律重新编码」。对已是 mp3 的数据再编码一次是纯粹的质量损失加无谓 CPU 开销，不做。

不内置 ffmpeg。

## 后果

**正面**
- 安装包保持在 Tauri 的 ~10MB 量级，不因音频处理而膨胀
- 无 ffmpeg 许可兼容性问题
- 无转码质量损失——拿到什么就是什么
- 下载即完成，没有第二阶段处理，Job 模型简化为单阶段
- 消除了整个跨平台二进制分发的负担

**负面**
- **即使账号有黑胶会员权限，也拿不到无损**。这是明确接受的取舍。
- 历史 `.ncm` 兼容分支中，若内部音频是 flac，无法转为 mp3。处理方式：**原样解密输出 flac 文件并在 UI 明示**，不做扩展名撒谎的降级（原脚本 `ncm_to_mp3.py:179-186` 在缺少 ffmpeg 时把 flac 改名为 .mp3，这是比失败更糟的行为，不予继承）。

## 实测验证（2026-07-26）

原本这是一条阻塞性前提——「320k 档返回 mp3」只是社区记录的行为，不是官方承诺，本 ADR 全部成立性依赖于此。现已用真实账号（黑胶会员，vipType=110）跑通验证：

| 项目 | 结果 |
| --- | --- |
| 接口声明 | `type=mp3`，`br=320000`，`size=11248370` |
| 实际下载 | 11,248,370 字节，与声明完全一致 |
| 文件头 | `49 44 33 04 00` → ID3v2.4，确为 mp3 |

**前提成立。零转码路线确认可行，不需要 ffmpeg，安装包无须为音频处理膨胀。**

验证账号本身持有无损权限，说明「放弃无损」是一次真实的取舍而非无谓的限制——是主动用它换掉了约 150MB 的跨平台 ffmpeg 二进制及其许可论证。

## 附带修正

原实现的两处缺陷不予继承，新实现必须正确处理：

- `ncm_to_mp3.py:127` 把 NCM 内嵌的专辑封面读出后直接丢弃
- 全程从未写入 ID3 标签，导致产物导入音乐库后显示为「未知专辑」

新实现必须从 API 元数据补全 ID3（标题 / 艺术家 / 专辑 / 封面），否则「方便使用」这个需求不成立——音乐库软件读的是 ID3，不是文件名。
