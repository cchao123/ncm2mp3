# ADR-0008：输出目录平铺，由应用内曲库页承担「方便使用」

- 状态：**已接受**
- 日期：2026-07-26

## 背景

原始需求第三条是「可以打开目录，这样方便使用」。

设计过程中出现一处需要澄清的矛盾：选择平铺目录的初始理由是「去重最好判断」，但既然已决定维护 SQLite 索引（ADR-0009），**去重依据是曲目 ID 而非文件名**，目录结构对去重完全无影响。平铺的理由因此消失，而它的代价——上千个文件摊在一个目录里——依然存在。

## 决策

**目录保持平铺**，文件名形如 `艺术家 - 歌名.mp3`。

「方便使用」这一需求**改由应用内的曲库页承担**：可搜索、可排序的已下载列表，点任意一首可直接在系统文件管理器中定位到该文件。

「打开目录」按钮保留，定位为逃生口，而非主要使用路径。

## 后果

**正面**
- 落盘逻辑简单，无需处理目录层级创建、艺术家名变更导致的目录迁移等问题
- 单曲下载不会造出大量只含一个文件的目录
- 曲库页基于已有的 SQLite 索引构建，边际成本低于新建一套目录管理逻辑

**负面**
- **直接把输出目录拖进 Plex / Navidrome 这类音乐库软件会很乱**。这是明确接受的取舍。缓解手段是 ID3 标签写全（ADR-0003）——多数音乐库软件按 ID3 而非目录结构编目，实际影响小于观感。
- 应用内曲库页成为必做项，不能砍。砍掉它，需求三就落空了。

## 文件名清洗（跨平台硬要求）

平铺 + 「文件名带全信息」意味着文件名承载了全部区分度，清洗规则必须严格：

- 按 **Windows 规则**统一清洗（它比 macOS 严格），保证同一份代码在两个平台产出相同文件名
- 处理 Windows 保留设备名（`CON`、`PRN`、`AUX`、`NUL`、`COM1`–`COM9`、`LPT1`–`LPT9`）
- 处理路径总长限制，超长时截断但保留可辨识度与扩展名
- 处理末尾空格与句点（Windows 下会被静默剥离，导致文件名与索引记录不一致）
- 同名冲突（同一首歌的不同版本）需有确定性的消歧后缀规则

### 不予继承的缺陷

原实现 `ncm_to_mp3.py:243`：无元数据时直接用原始文件名兜底，**完全跳过清洗**。清洗只在 `get_song_name` 的元数据分支内执行。新实现中，**清洗必须是落盘路径上的唯一出口**，不存在绕过分支。
