# 设计文档

从「NCM 转换脚本」到「网易云桌面客户端」的设计记录。产出自 2026-07-26 的一次设计访谈。

- [术语表](glossary.md) —— 域内词汇的唯一含义

## 目标形态

一个 Tauri 桌面应用（macOS + Windows）：扫码登录 → 浏览歌单/搜索 → 下载 → 落盘为 MP3 → 应用内曲库页管理。

## 决策一览

| ADR | 决策 | 主要代价 |
| --- | --- | --- |

| [0009](adr/0009-task-lifecycle.md) | SQLite 索引，关窗即暂停 | 无后台下载 |

## 硬约束

1. **只下载当前账号权限范围内的曲目**，不实现任何绕过版权限制的能力（ADR-0001）
2. **直链必须逐首现取**，不可批量预取——链接会过期（ADR-0005）
3. **文件名清洗是落盘路径上的唯一出口**，不存在绕过分支（ADR-0008）
4. **凭据不得进入日志**（ADR-0004）

**第 1 步 · 最小闭环**
登录 + 我喜欢的音乐 + 串行批量下载 + SQLite 索引 + ID3 写入。
此步完成后应用已真正可用，覆盖备份场景的主要需求。

**第 2 步 · 曲库页**
已下载列表、搜索排序、定位到 Finder、打开目录。需求三在此闭合。

**第 3 步 · 歌单浏览**
复用第 1、2 步的列表与下载组件。

**第 4 步 · 搜索 + 单曲/专辑**
需先解决曲目可用性状态的 UI 表达。

**第 5 步 · 打包分发**
macOS 公证、Windows 签名。仅在确定要发给他人时投入。

**兼容分支（可随时插入）**
历史 `.ncm` 文件的解密。移植时用 `target/` 下的样本与 `output/` 下已知正确的产物做逐字节回归验证。

## 原实现中不予继承的缺陷

### ⚠ 首要发现：原脚本从未正确解密过任何文件

`ncm_to_mp3.py` 在 README 中标注为「主转换脚本，推荐使用」，但它**产出的每一个 mp3 都是不可播放的乱码**。

根因在解密流程第 9 步：元数据段之后应跳过 CRC32(4) + gap(5) 共 **9** 字节，原代码只跳了 5。后续读到的 `image_size` 落在 gap 的全零字节上而恒为 0，封面段被当作音频起始，整个音频流偏移错位。

实测（`target/刘鸿 - 站台.ncm`）：

| | 前 4 字节 | 结论 |
| --- | --- | --- |
| 修复前 | `d0 73 52 e0` | 既非 ID3 也非 MPEG 帧同步，损坏 |
| 修复后 | `49 44 33 04` | 正常 ID3v2.4 |

`output/` 目录下那三个可播放的 mp3 **并非此脚本产出**，而来自 `批量转换.sh` 调用的第三方 `ncmdump`。

**修复已验证**：改为跳 9 字节后，产物音频流与 ncmdump 产物 **12,379,950 字节逐字节完全一致**。二者互为印证，`output/` 可作为 Rust 移植的可信回归基准。

### 缺陷清单

| 位置 | 问题 | 状态 |
| --- | --- | --- |
| `ncm_to_mp3.py` 第 9 步 | 跳 5 字节应为 9，音频流整体错位，**解密从未成功** | ✅ 已修 |
| `ncm_to_mp3.py:173` | `subprocess` 在函数内延迟导入，FLAC→MP3 路径必抛 `UnboundLocalError`，**该路径从未跑通** | ✅ 已修 |
| `ncm_to_mp3.py:159` | `b'IDV'` 系 `b'ID3'` 笔误 | ✅ 已修 |
| `ncm_to_mp3.py:179-186` | 缺少 ffmpeg 时把 flac 改名为 `.mp3`，产出扩展名撒谎的文件 | 移植时不予继承（ADR-0003） |
| `ncm_to_mp3.py:127` | 内嵌专辑封面读出后直接丢弃 | 移植时修正 |
| `ncm_to_mp3.py:243` | 无元数据时用原始文件名兜底，跳过全部清洗 | 移植时修正（ADR-0008） |
| 全局 | 从未写入 ID3 标签，产物导入音乐库显示为「未知专辑」 | 移植时修正（ADR-0003） |

> 教训：两个独立实现（本脚本与 ncmdump）产出的音频流逐字节比对，是这类二进制解密移植唯一可靠的验收方式。肉眼看代码看不出偏移错位——它不报错，只是安静地产出垃圾。
