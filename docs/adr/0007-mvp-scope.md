# ADR-0007：MVP 范围包含搜索与单曲/专辑下载

- 状态：**已接受（附风险提示）**
- 日期：2026-07-26

## 决策

第一个可用版本包含的下载入口：

- 我喜欢的音乐
- 歌单浏览与批量下载
- 搜索
- 单曲下载
- 专辑下载

即完整的客户端式浏览体验。

## 风险提示

本决策与 ADR-0006（Rust 原生重写加密层）叠加后，构成一个需要显式管理的排序风险：**范围最大的 UI 工作 + 风险最高的底层实现**。

缓解措施已写入 ADR-0006 的排序约束——加密层 spike 必须先于任何 UI 工作完成。在 spike 通过前，本 ADR 列出的所有入口都不应动工。

## 由搜索入口引出的问题 —— 已解决

一旦提供搜索，用户必然会搜到**账号权限之外**的曲目（无版权、需单独购买、地区限制）。

按 ADR-0001 的硬约束，这些曲目**不下载、不绕过**。因此 UI 必须能明确区分并表达曲目的可用性状态，而不是让用户点击后遇到一个语焉不详的失败。

### 状态枚举与判定方式

搜索走 `cloudsearch/pc` 而非老的 `search/get`——**前者的结果带 `privilege` 字段**，这是能否在点击前判断权限的关键。

判定优先级（`client.rs::parse_availability`）：

| 条件 | 状态 | UI 表现 |
| --- | --- | --- |
| `privilege.st < 0` | `Unavailable` | 标「无版权」，置灰不可选 |
| `privilege.dl > 0` | `Downloadable` | 正常，可勾选 |
| `fee == 4` | `PayAlbum` | 标「需购买」，置灰 |
| `fee == 1` | `VipOnly` | 标「需会员」，置灰 |
| 其余 | `Unavailable` | 置灰 |

以 `dl`（当前账号可下载的最高码率）为首要判据——服务端已把账号权限算进去了，比自行拿 `fee` 与 `vipType` 对着推可靠。

**这只是预判，不是保证。** 真正的判据仍是 `song/url` 是否返回非空直链；预判的价值在于让用户在点击之前就知道哪些下不了。实际下载时若仍失败，按 ADR-0009 记为终局失败、不重试。

### 双重防线

前端置灰不可勾选，后端 `enqueue` 再过滤一次非 `Downloadable` 的曲目。后者不是冗余——即便前端漏筛，也不该让下不了的曲目白白消耗请求配额（ADR-0005 的风控考量），最终还是要落进失败清单。

## 实现顺序的实际调整

原计划把搜索排在第 4 层。实际开发中用户明确以「搜索 → 下载」为主要用例，因此**搜索提前实现并设为默认页**，歌单浏览保留但降为次要入口。

这个调整不影响 ADR-0006 的排序约束——加密层 spike 仍然先于所有 UI 完成。

## 建议的实现顺序

范围虽大，落地应分层，每层可独立交付：

1. **Spike**（ADR-0006）——加密层可行性验证
2. **登录 + 我喜欢的音乐 + 批量下载** —— 最小闭环，此时应用已经真正可用
3. **歌单浏览** —— 复用第 2 层的下载与列表组件
4. **搜索 + 单曲/专辑** —— 需先解决可用性状态的表达问题

第 2 层完成即已覆盖备份场景的主要真实需求；第 3、4 层是体验扩展。这个顺序让每一步都有可交付物，而不是几周后才第一次看到东西能跑。
