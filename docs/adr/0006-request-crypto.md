# ADR-0006：请求加密层用 Rust 原生重写，但必须先以 spike 验证

- 状态：**已接受 · spike 已通过**（2026-07-26）
- 日期：2026-07-26

> **实测结论（先读这段）**
>
> 1. **weapi 一次算对**，含本文警告的 RSA 非标准填充。服务端返回 `code:200` 与有效 unikey。
>    Rust 原生路线成立，无需退回 sidecar，ADR-0002 的体积优势保留。
> 2. **只需要 weapi，不需要 eapi**。见下方「eapi 的处置」。
> 3. 扫码登录三步、账号、歌单、直链、下载全流程跑通，产物为 320k mp3。

## 背景

按 ADR-0001，主链路依赖网易云的非官方接口；按 ADR-0002 选用 Tauri，实现语言为 Rust。

调用这些接口必须复现客户端的参数加密约定。社区逆向记录中主要有两套：

- **weapi**：请求参数经两段 AES-128-CBC 加密，会话密钥随机生成后用 RSA 包裹，随请求发送 `params` 与 `encSecKey`
- **eapi**：AES-128-ECB，请求体包含接口路径、明文数据与摘要校验

Node 有 NeteaseCloudMusicApi、Python 有 pyncm 这类持续维护的成熟实现，**Rust 生态中没有同等量级的对应物**。

备选方案是把 Node/Python 实现打包为 Tauri sidecar 子进程，风险低但会使安装包从 10MB 涨到 50-100MB，且需为三个平台靶各备一份，基本抵消 ADR-0002 选择 Tauri 的核心理由。

## 决策

**用 Rust 原生重写请求加密层**，不引入 sidecar。

## 已知实现陷阱

weapi 的 RSA 环节**不是标准填充**。社区实现中普遍需要手工处理：将 16 字节会话密钥按特定顺序处理后左侧补零至 128 字节，再直接做模幂运算。直接调用 crate 的 PKCS#1 v1.5 加密会得到服务端拒绝的结果，且错误信息不会指向真正原因。

这是本项目最可能卡死人的单点。

**调试手法**：把随机会话密钥临时固定为常量，用同样的常量跑一遍社区的 JS 实现，逐字节比对两边产出的 `params` 与 `encSecKey`。加密链路带随机数时无法直接对照，固定随机数后即可精确定位是哪一段算错。

## 排序约束（重要）

本 ADR 的实现**必须排在所有 UI 工作之前**，作为项目第一个里程碑。

理由：MVP 范围（ADR-0007）包含搜索、专辑、歌单、单曲多个入口，对应多页 UI。若加密层最终不可行，这些 UI 全部作废。把最高风险项放在最后验证是错误的排序。

### 里程碑定义：Spike（约半天）

单一目标——用真实账号跑通：

1. 取 unikey → 生成二维码 → 轮询至 `803` 拿到 Cookie
2. 用该 Cookie 请求 `song/url` 的 `exhigh` 档，取到一条直链
3. 下载该直链，确认文件头确为 mp3 且可正常播放

三步全通过，Rust 原生路线成立，继续。
任一步卡住超过预设时限，退回 sidecar 方案并修订 ADR-0002 的体积预期。

顺带这个 spike 也验证了 ADR-0003 的阻塞性前提。

## eapi 的处置：不采用

原计划用 eapi 的 `song/url/v1` 配 `level=exhigh` 取直链。实测该接口**稳定返回 HTTP 200 + 空 body**。

排查过程（记录下来，避免以后有人重走）：

| 排除项 | 方法 | 结论 |
| --- | --- | --- |
| 加密实现有误 | 与独立 Python 实现逐字节比对 eapi 产物 | **完全一致**，加密无误 |
| 摘要路径写错 | 确认用 `/api/...` 而非 `/eapi/...` | 已正确 |
| 缺少内嵌 `header` | 在请求体中补全客户端标识字段 | 仍为空 body |
| `os` 取值不对 | 分别试 `pc` / `android` / `iphone` | 三者皆空 |
| 响应被压缩 | 检查 `Content-Encoding` | 无压缩，就是 0 字节 |

**改用 weapi 的 `song/enhance/player/url`，以 `br=320000` 表达音质，实测直接可用。**

由于 ADR-0003 已确定目标音质固定为 320k，`level` 参数带来的额外表达力（无损档位）本就用不上，因此不再追查 eapi。

**这带来一个额外收益**：整个项目只需维护 weapi 一套加密约定，需要跟踪的逆向面缩小一半，长期维护成本相应下降。

`crypto::eapi` 的实现已验证正确，予以保留但不接入主链路——若将来 weapi 侧接口失效，它是一条现成的备选路径。

## 后果

- 成品为单一二进制，Tauri 的体积与启动优势完整保留
- 接口失效或加密约定变更时，无法依赖上游社区修复，需自行重新逆向。这是持续维护成本，不是一次性成本。
- 需要额外准备一份独立实现作为调试对照物（仅开发期使用，不进入分发产物）。本次 eapi 排查已证明这个手法的价值：**逐字节比对能在几分钟内排除「加密写错了」这一整类猜想**，把注意力直接引向请求层。
