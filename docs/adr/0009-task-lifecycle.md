# ADR-0009：SQLite 索引承载去重与续传，关窗即暂停，失败跳过并汇总

- 状态：**已接受**
- 日期：2026-07-26

## 背景

保守串行策略（ADR-0005）使批量任务可能持续数小时，长时任务的行为必须显式设计。

## 决策

### 1. 维护本地 SQLite 索引

至少记录两类信息：

- **曲库**：曲目 ID、落盘路径、来源、完成时间
- **任务队列**：待下载曲目、状态、失败原因

三项能力挂在它上面：**按曲目 ID 去重**、**断点续传**、**列表中显示「已下载」标记**。ADR-0008 的应用内曲库页也构建于此。

### 2. 关窗口即暂停，重开续传

关闭窗口停止当前队列，进度已在 SQLite 中。下次启动时提示是否继续未完成的任务。

不做托盘常驻与后台下载——避免托盘生命周期、系统通知、macOS 与 Windows 行为差异这一整块跨平台工作。

### 3. 失败跳过，最后汇总

任何单曲失败都不中断队列。全部跑完后展示失败清单，含分类原因。

**实现层面的必要补充**：几小时的串行任务必然遭遇瞬时网络抖动，若不加区分地把它们计入失败清单，一次 WiFi 波动就能让几十首歌无谓失败。因此对明确的瞬时网络错误做**有限次即时重试**。

这不违背上面的决策——用户可见行为仍然是「队列不中断、最后给清单」，重试只是让清单里不出现本可避免的条目。权限类失败（无版权、需购买、地区限制）重试无意义，直接记录跳过。

## 索引与磁盘的一致性问题

SQLite 索引会与磁盘实际文件不同步——用户可能在 Finder 里手动删除或移动了文件，而索引仍标记为「已下载」。

处理方式：**在决定跳过某首歌之前校验文件确实存在**，而不是只信索引。文件缺失则视为未下载并重新加入队列。这是把校验放在正确的时机上，而不是启动时全量扫盘（上千首会拖慢启动）。

## 后果

- 引入数据层，以及索引 schema 演进的迁移问题
- 长时任务变得可中断、可恢复，符合真实使用节奏
- 关机或强制退出后，最坏情况只丢失当前正在下载的那一首
- 不做后台下载意味着用户必须让窗口开着——这是为砍掉跨平台后台生命周期工作而付出的明确代价
