# ADR-0005：保守串行下载，逐首取链

- 状态：**已接受**
- 日期：2026-07-26

## 背景

高频调用非官方接口会触发服务端风控。后果轻则接口临时返回失败，重则**账号受限**——而这里用的是用户日常听歌的真实账号，代价不局限于本工具。

风控阈值不公开也不固定，无法通过设计推算出「安全并发数」。

## 决策

**串行下载，每首之间插入随机间隔。**

不做并发。宁可慢。

节流参数（间隔上下界）必须做成可配置项而非硬编码常量——因为「多保守才算保守」无法先验确定，只能实际跑过再调。

## 关键约束：直链必须逐首现取

直链有**有效期**。这否决了一种看似自然的实现：

```
❌ 先批量取回 500 首的直链 → 再排队下载
```

队列跑到第 400 首时，一小时前取的链接大概率已失效，且失败原因会伪装成网络错误，极难排查。

正确做法：

```
✓ 取第 N 首的链接 → 立刻下载第 N 首 → 随机间隔 → 取第 N+1 首的链接
```

串行策略恰好天然满足这个约束。**这条约束必须显式写在代码注释里**——否则未来任何一次「优化成批量预取」的改动都会重新引入此缺陷。

## 后果

- 上千首的「我喜欢的音乐」首次同步可能需要数小时。这使**长时任务的生命周期设计成为一等公民**（见 ADR-0009），而非事后补丁。
- 账号受限风险降到实际可控范围
- 用户可见的进度反馈变得重要——几小时的任务必须能随时看清「跑到哪了、还剩多少、失败了几首」
